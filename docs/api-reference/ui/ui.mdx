# UI

Entry point for the UI message manager. Use `Panel` to obtain a handle for a logical UI panel; the panel id binds to the panorama-side panel script registered with the same id via `DW.registerPanel({ id: "..." })`.

A panel stays up until you destroy it, the player leaves, or the map changes. Every panel is gone on a new map, so treat any you were tracking as closed in `IDeadworksPlugin.OnStartupServer` and show them again as players arrive.

### UI.MaxFramesPerSecond {#maxframespersecond}

Frames per second this channel can actually deliver, derived from `CaptionLengthSeconds` and the client's six-caption display pool. Read-only.

Pace recurring updates against this. Offering frames faster than the channel drains does not increase throughput — it just grows the queue and adds latency, because a frame is only as useful as the moment it arrives. Your achievable byte rate is roughly `MaxFramesPerSecond × bytes-per-update`; to go faster, send more per frame rather than more frames.

### UI.CaptionLengthSeconds {#captionlengthseconds}

How long each caption frame lives on the client, in seconds. Defaults to 0.2.

This governs throughput, not bandwidth. The client renders at most six captions at a time and silently discards any beyond that, so the channel tops out at `6 / CaptionLengthSeconds` frames per second — about 5/s at the game's default linger, which is why the transport felt slow regardless of rate or frame size. The send rate is clamped to stay inside this automatically.

Lower means more throughput but less time for the client to build its panel and for the mod to read it. Do not go near a frame time.

### UI.CaptionLingerSeconds {#captionlingerseconds}

The client's `cc_linger_time`, which is added to every caption's own length to get its expiry. Defaults to 0.3, matching what the addon asserts on the client.

This is not a knob you set to change client behaviour — the addon owns that. It exists so `MaxFramesPerSecond` tells the truth. If you ship an addon with a different `CC_LINGER`, set the same value here or the channel will pace itself against a pool that recycles slower than it thinks.

### UI.MaxFrameLength {#maxframelength}

Bytes of wire payload per caption frame. Defaults to 3800.

Hard-capped just under 4000: the client copies caption text into a fixed `char[4096]` stack buffer with no bounds check, so larger frames corrupt its stack. Larger frames are otherwise strictly better — each frame costs one usermessage, so fewer/fatter frames means less reliable-channel pressure for the same payload.

### UI.ClientPanels() {#clientpanels}

Panel ids the client at `slot` supplies its own layout for, reported on the handshake. Empty until that client acks.

Sending a layout for one of these replaces the client's own tree, which is almost never what you want — check here before shipping a panel whose id an addon might also claim.

Empty means unknown, not none: a stock client and one whose addon predates the field both report nothing. Use it to avoid stepping on a panel you know about, not to prove one isn't there.

## Events

### UI.ClientResync {#clientresync}

A client discarded its UI and needs its layouts re-sent. The argument is the player slot.

The client tears everything down if server frames stop arriving for a few seconds — a hitch is enough — and it cannot rebuild on its own, because layouts live on the server. Any plugin that ships a panel should re-send it here, otherwise that player's UI stays blank until they reconnect. Re-sending is idempotent: precache/show simply replaces whatever the client had.
